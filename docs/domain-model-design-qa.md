# Domain model design QA

This separate skeptical pass reviews [the design](domain-model-design.md) before production edits. Probes and qualifications use synthetic cases and ignored artifacts. Source review is not owner approval.

| Challenge | Evidence and resolution |
| --- | --- |
| The documented date rule already works for all edits. | Native FSI probes return FutureDate for unchanged accepted notification and decision dates after clock rollback. Correction has the required changed-date comparison. Share that policy across ordinary changes and corrections, with a new-future-incident control even when notification is unchanged. |
| Parsed inputs could silently canonicalize retry identity. | Operation.prepare validates then hashes RequestRecord.encode of the original CommandRequest. Keep that original request boundary and byte vectors; normalized internal inputs are used only to decide state. |
| Eliminating validation could bypass native admission or change refusal precedence. | Keep envelope/payload admission before case lookup, stale revision and eligibility. Reuse its parsed result inside a single decision; preserve independent Application admission before identity hashing and Domain execution against locked current state. |
| A generic correction choice could allow registration CLEAR or contradictory booleans. | Use distinct tagged validated groups, matching the public allowed actions. No registration CLEAR, Replaced/Cleared flag combinations or externally supplied KEEP value. |
| Moving final validation changes paid acknowledgement or no-op behavior. | Preserve acknowledgement checks against the original request tags and accepted progress before constructing the candidate. Compare typed fact/progress values, so equivalent amount spelling cannot create a correction-only revision. Exercise the full independent combination matrix. |
| Chronology and positive payment could drift between restore and mutation. | Apply one state validator to both paths, after scalar parsing. Test partial tuples, zero-paid snapshots, reversed dates and every supported closure/payment axis. |
| Correcting prose alone sufficiently records changed behavior. | Machine identity excludes editorial prose; increment the executable rule revision. SQL independently hard-codes 1 and must change with readers/writers, fresh baseline and generated catalog. Require real-row evidence and refusal of wrong/terminal revisions. |
| Primary acceptance proves every reconciliation reader is updated. | Real PostgreSQL acceptance succeeded but exact replay/recovery failed: encrypted witness candidates and ordinal primary matching separately hard-coded rule revision 1. Extend the revision ownership decision to both producers and both sides of witness reconciliation; repeat complete database qualifications rather than count the earlier failing run. |
| New revision support should upgrade old installations. | Existing checksum-bound baseline admission refuses incompatible bytes. Update one fresh baseline; retain refusal and non-destructive initialization qualifications. No historical rule interpreter or migration engine. |
| Scalar metadata consolidation could change admission or wire bytes. | Amount definitions independently repeat 18/17/4/23 and currency repeats 3. Derive grammar and budgets from the existing fixed counts; independent maximum/over-limit scalar properties and contract byte verification must remain unchanged by this consolidation. No configurable scalar framework. |
| New types or shared validation justify architectural expansion. | All new types remain Domain-internal, with the existing public Claim signature and nine raw commands. No new component, dependency, business field or public raw-field binder. |
| A passing self-derived command list is sufficient. | Keep the independent availability matrix; add an independent correction action/state oracle and negative controls. Required real PostgreSQL, contract, published client and coverage jobs remain conjunctive. |

The design is approved for implementation as an agent design decision. It retains existing product boundaries for concrete reasons and addresses every demonstrated finding in scope. Implementation feedback that contradicts an assumption requires revisiting that decision before continuing.
