# Persistence, transactions and recovery audit

Audit source: `dad3737360f03fabbcb5336c6de6d132fa7c936d`. Its architecture PR is now merged;
the equivalent submission base is `bd7af43940bbb5a5d8883e86545f89e4596f5cf4`.
The [separate design QA](persistence-recovery-design-qa.md) challenges these decisions before implementation.

| Boundary | Finding and decision | Failure scenario and evidence |
| --- | --- | --- |
| Command writer | Ordinary commands use retained preparation, witnessed attempt admission and RecoveryExecutionStore. IClaimStore.Transact/Service/StoreTransaction supply a second writer, used by receipt verification and numerous persistence tests, without that protocol. Remove the production transaction member and duplicate writer; retain one accepted-state persistence collaborator. Test fixtures must use the actual retained-attempt writer; in-memory mutations remain explicitly test-only. | A revoked preparation must never execute through an alternate writer. Concurrent operation/case tests must exercise the writer the product uses, with actual attempts and settlements. |
| Exact accepted replay | ActorOperationReadStore.Accepted reads primary rows without witness reconciliation. Retain, Start and Dismiss also have primary-only accepted shortcuts. A committed primary row is necessary but does not replace independent settlement. Centralise content-bound accepted observation with primary authority, operation identity, current actor grants and witness proof. Mutation calls may reconcile exact committed evidence; read-only calls verify without appending. | Primary COMMIT succeeds, W1 fails, then Prepare/Execute/Resolve or a retention/admission/dismissal shortcut observes the row. No definite receipt while settlement remains unconfirmed; a healthy exact retry settles once without another case revision. Wrong content must refuse before decoding/disclosing a receipt. |
| Current reads and history | Primary projections and historical receipts also need independent evidence. Verify each disclosed current snapshot against its accepted snapshot and exact settled witness candidate, under existing primary/grant and witness read fences. Reads never append settlement. | A primary acceptance commits but W1 fails: Get/List/History/Observe refuse the unconfirmed projection until a mutation-bound exact retry settles it. An unrelated unavailable witness cannot turn primary rows into authority. |
| Receipt verification | ObservedReceiptVerification invokes the second writer after an earlier receipt lookup. Replace that with content-bound witnessed observation; observation cannot become fresh execution. | Accepted material is missing or changes between observations: return a refusal/unknown outcome rather than invoke Domain and create a new acceptance. Exact replay does not capture a new business date. |
| Lease cleanup | AuthorityOperationFence retires a connector after failed unlock but rethrows during Dispose. This can replace an already witnessed result with mutation uncertainty. Retire the ambiguous connector without rewriting the caller's observed result. | Terminate the synthetic primary connector after work completes; the known result survives and no session lease re-enters the pool. Acquisition cancellation still propagates and retires its connector. |
| Recovery snapshots | Recovery detail reads use multiple READ COMMITTED statements; owner preparation pruning does not take the primary authority row lock. Use one repeatable snapshot for header, authority and attempt evidence. Preserve primary-first locking and the independent disclosure fence. | Prune a terminal preparation between header and attempt reads: the response must represent one snapshot, not retained metadata combined with newly absent evidence. Pending/unsettled preparations remain unprunable. |
| Historical attempt knowledge | An accepted shortcut can settle an older admitted attempt from a different later acceptance. Distinguish observed accepted receipts from a new acceptance and leave historical attempt settlements unchanged. | An earlier unknown/rejected attempt is followed by a successful fresh attempt. Reusing the old identity may observe the exact receipt, but cannot infer or rewrite that old attempt’s result. |
| Attempt identity | Execution checks attempt existence before deciding, but a settled attempt can be reused and only discovered after a witness intent is issued. Admit only an operation-bound unsettled attempt before any new Domain decision or witness intent. Existing accepted/revoked authority remains first. | Reuse a rejected attempt after the business date/state changes: no new intent, revision or rewritten settlement. A new independently admitted attempt can execute. |
| Revocation event identity | Acceptance and revocation currently share the same witness INTENT identity. An orphan acceptance intent consequently prevents durable revocation of future unaccepted authority. Give revocation a distinct deterministic event identity, bind it in the fresh primary schema and update reconciliation, audit and purge coverage. Preserve the original command ID and every earlier uncertain attempt. | A crash leaves an acceptance intent but no primary effect. Dismissal may fence future execution while leaving the original intent and attempt unresolved; it must not claim the earlier attempt failed or permit pruning it. |
| Canonical identity | PreparedOperation privately binds request, canonical bytes and digest but returns its owned mutable byte array. Return a defensive copy. Keep authored scalar spelling and canonical format unchanged. | Mutating a returned buffer cannot alter the subsequently persisted request or separate its digest from its bytes. Existing strict canonical/snapshot and signed-artifact qualification remains required. |
| Locks and uncertainty | Retain primary authority before operation/case locks, cross-process authority leases through post-COMMIT witness settlement and audit's exclusive drain. Keep commit-start uncertainty, orphan-intent refusal and independent historical attempt knowledge. | Post-COMMIT response loss, concurrent exact/conflicting retries, grant revocation, writer handoff and pending audit must not infer rollback, rebase requests or erase earlier uncertainty. |
| Hold-bound preparation retention | Terminal preparation pruning can discard provenance and attempt evidence while a case hold remains active. Exclude both active lifecycle holds and unreleased erasure holds, and take the primary shared authority lock before operation locks so a new hold cannot race deletion. | An accepted preparation is old enough for owner pruning but has a witnessed hold. It remains retained until an explicit witnessed release; the owner cannot infer release from its review date. |
| Schema and retention | Retain untyped numeric plus exact scale/range checks, complete tuples, chronology, immutable installation calendar, exact catalog/baseline admission, terminal-only pruning and active-export/unsettled-attempt exclusions. Add only the revocation event binding to the checksum-bound fresh baseline; refuse the earlier baseline untouched. | SQL overprecision refuses without rounding; invalid snapshots and altered protections refuse; accepted receipts and revocations outlive technical preparation retention. Fresh initialization and restored-pair qualification remain separate. |

Keep the modular monolith and independent witness. Distributed transactions, automatic rollback of orphan intents, retry rebasing, migration engines and a generic workflow framework would weaken or complicate the stated authority model. Implement only reviewed repairs and their dependents: native ports and fixtures, compiled architecture controls, inventories, owner contracts and complete required verification. Private experiments and reports remain ignored; no adopted database or retained installation is changed.
