# Owner-only managed backup qualification

`managed.py` is a bounded backup/copy and quarantine-inspection component for the new fresh-installation design. It is not a case-work command, a promotion command, or evidence that two containers on one Mac have independent custody. Never point its services, archive root, or restore hook at an adopted installation without a separate owner-approved operational plan. The included qualification uses only disposable synthetic PostgreSQL containers and destroys its own exact-labelled containers and temporary files.

Use PostgreSQL **18.6** `psql`, `pg_basebackup`, and `pg_verifybackup`, age **1.3.2**, Python **3.12 or newer** with `tarfile` extraction filters, OpenSSL with Ed25519 support, jq, Docker, and Bash. `managed.py` checks the Python, PostgreSQL and age versions before backup or inspection. Install the maintained releases with the host's appropriate package manager; Homebrew is only one way to provision this Mac. These versions matched [PostgreSQL's 18.6 release](https://www.postgresql.org/docs/release/18.6/) and [age's latest v1.3.2 release](https://github.com/FiloSottile/age/releases/tag/v1.3.2) when this tool was written. Keep the PostgreSQL client minor aligned with the pinned server image. Do not downgrade the client or crypto tool to make a failed qualification pass.

Configuration is an owner-private JSON file (`0600`) outside the repository, with no symlinked path components. `archiveRoot`, `checkpointRoot`, and `inventoryRoot` are existing private directories (`0700`); the latter two are disjoint from the archive. Checkpoints and signed attestations must be separately custodied and off-host for real data; different directories on one machine are not independent failure domains. The COPY_ATTESTOR and CHECKPOINT Ed25519 keys are distinct and separately purposed, and the owner-only HMAC commitment key is separate from witness event-encryption and age decryption keys. Different key files or custodian labels on one Mac do not prove independent human or host control. The owner configuration specifies both signer IDs and custodian labels, encryption key ID, backup interval, maximum verified-backup age, restore horizon, backup/WAL retention and longer checkpoint retention; signed inventory contains keyed commitments, not plaintext custodians or locations. `ageIdentity` is used only in a quarantined inspection environment. `maxBackupBytes`, `maxTarEntries`, and `maxWalCopies` bound decrypted bytes, extracted entries, and archive inventory work; tune them to measured installation size without making them unbounded. `primary` and `witness` each name distinct libpq `metadataService` and `replicationService` profiles from an owner-private `PGSERVICEFILE` pinned by exact file SHA-256; those profiles carry credentials without putting them in argv or logs. Remote profiles must use `sslmode=verify-full` with a private pinned CA file and DNS hostname for both metadata and replication; only the isolated synthetic fixture admits loopback profiles. Ambient libpq connection overrides are removed. The metadata role needs the installation row and PostgreSQL control-data functions; the backup role needs replication privilege. The archiver uses a **different minimal configuration** with only `format`, `archiveRoot`, and `ageRecipient`; it must not receive signing, commitment, or decryption keys.

The capture configuration contains only the CHECKPOINT public key, signer ID and private socket path—not its signing key. Run the fixed `CheckpointSigner.py --config <signer-private-config>` as a separate custodian process before capture. Its `0600` config holds the CHECKPOINT private/public key paths, CHECKPOINT purpose, installation identity, one private socket and a private replay ledger; it signs the exact canonical checkpoint and returns the same detached Ed25519 signature for an exact retry. A changed cycle candidate, wrong role/key/identity or missing socket refuses. The one-Mac test uses distinct processes and keys but cannot prove separate host or administrator control. For real use, the closed `REMOTE_SSH` mode instead requires a separately root-signed `claimcore-checkpoint-signer-topology-1` matching the current installation, CHECKPOINT public key, distinct host/admin/storage and exact Ed25519 SSH host-key pin. It invokes only the fixed remote `/usr/local/libexec/claimcore/CheckpointSigner.py --stdio-sign` under `/var/lib/claimcore/checkpoint-signer/config.json`, with no ambient SSH config, proxy or caller-selected executable. This Mac has no witnessed publication root or separately administered signer host, so that mode remains fail-closed operationally; the local socket does not satisfy real-data custody.

The direct `managed.py capture` command is removed. `Test-ManagedBackupPrimitives.py` runs this older unfenced path only against two exact-labelled disposable synthetic containers whose PostgreSQL system IDs match its service profiles. It streams each cluster's full `pg_basebackup` tar, including the WAL needed to recover that base backup, directly into age encryption, then signs a data-minimal cycle manifest, witness-tip checkpoint, and one canonical detached-Ed25519 REGISTER attestation per base copy. The attestations bind PostgreSQL system ID, timeline, backup-manifest digest and WAL range, segment size, witness cutoff, ciphertext digest/length, key IDs, retention and keyed custodian/location commitments. They explicitly say `UNVERIFIED` and `NOT_REGISTERED`: local signing is not a witnessed primary inventory event. Each cycle has a fresh opaque ID. The current manifest is explicitly `unfenced-capture`: sequential base backups and a later checkpoint **do not** establish a common cross-cluster authority cutoff if writes continue. This lower-level tool never marks a restore `full`; the separately anchored product report and W1 tail supplement have their own verifier. Continuous WAL archiving is separate: configure the PostgreSQL `archive_command` for each cluster to call `managed.py --config <archiver-config> archive-wal <primary|witness> %p %f`; test that the server reports successful archival and that both independently custodied encrypted copy locations have acknowledged it. Then run owner-only `attest-wal <cluster> <segment>` to decrypt-check and sign each WAL copy. This still emits `UNVERIFIED`/`NOT_REGISTERED` and cannot prove WAL freshness, recoverability or erasure deletion. Archive failure must be treated as a mutation-admission failure by the service; a base backup alone is not a bounded restore horizon. The current archiver writes one encrypted WAL object and a checksum sidecar; loss of the sidecar after a crash is an `UNKNOWN` copy requiring owner reconciliation, not proof of deletion.

`Capture-FencedBackup.py --config <private-config>` is the separate supported owner-held capture path. The local socket mode additionally requires `--synthetic-only` and `_test` databases; `REMOTE_SSH` requires the root-signed fixed remote signer topology. It launches only the fixed packaged `ClaimCore.Database hold-backup-capture` command over an inherited private duplex descriptor; no owner-selected executable or barrier Boolean is accepted. Only an owner-issued nonce-bound HELD lease with an empty private cycle root permits both encrypted BASE streams. The exact signed cycle manifest and independent CHECKPOINT-signed checkpoint bind that lease, installation/generation/cutoff, maintenance-evidence digest, ciphertext hashes and PostgreSQL backup metadata while retaining the truthful `unfenced-capture` source label. The owner command must reopen the five FINISH files under nofollow private handles, recheck the held authority cutoff, then persist and reread an exact local private cycle receipt. This local receipt is not itself a witnessed backup-cycle authority event or independent proof that the historical service was quiescent. The script prints `CAPTURED_UNVERIFIED` only after SEALED plus OBSERVED; pre-FINISH failure sends ABORT, post-FINISH uncertainty retains the private files and reports `CAPTURE_UNCONFIRMED`. This receipt does not register or retain the copies, pass a restored-pair audit, issue backup-health authority, or establish off-host custody. The native owner-held path is wired, but its local receipt is not itself a witnessed backup-cycle authority event; off-host CHECKPOINT custody, signed publication root, retained copy registration/physical verification and complete restored-pair/WAL audit remain required before any real-data readiness. Direct `managed.py capture` CLI is removed; the unfenced primitive is available only through the exact-labelled synthetic test fixture.

`inspect <cycle-id> --restore-verifier <executable>` is only a lower-level synthetic backup-primitives drill. It validates its signed manifest and retained checkpoints, decrypts into a private temporary directory, and runs `pg_verifybackup` on both copies before supplying them to a test callback. It accepts only `synthetic-only` callback results and always returns `promotionAuthorized:false`; no configured callback hash or owner-selected executable can elevate it to a product report. `Verify-BackupPrimitives.sh` is the tiny-oracle test callback. Its recovered-row probes are not ClaimCore schema admission or full DataAudit. The separate `Restore-IsolatedTestPair.sh` Integration fixture uses real fresh ClaimCore primary and witness baselines, encrypted base backups and WAL, two physical restored PostgreSQL clusters, `pg_verifybackup`, and auditor-only full current-pair audit; this remains local synthetic functionality evidence, not a signed recoverability or production certificate.

`Verify-ManagedCopy.sh <owner-private-input.json>` is the fixed packaged verifier for one encrypted managed BASE or WAL object; it accepts no caller-selected verification callback. It independently hashes the ciphertext through a private no-link path, decrypts under bounded owner-private scratch, checks a BASE with PostgreSQL 18.6 `pg_verifybackup` and a network-isolated boot/recovered identity and nonpayload row count, or checks an exact WAL segment's size, filename timeline and first parsed record. It emits canonical ASCII JSON plus a detached Ed25519 signature under the distinct `RESTORE_COPY_VERIFIER` purpose, binding the copy event/revision, opaque object, witnessed cutoff, ciphertext and decrypted digests, fresh nonce, holder/key IDs and short expiry. Its signed location commitment is metadata supplied by custody; the verifier does not hold the separate owner HMAC key. The product owner `verify-managed-copy` transition must independently validate the registered key/current human holder, witnessed ledger event and location commitment, rehash the exact private object, and co-commit any `RETAINED` state. A script proof alone neither changes copy state nor certifies a restored pair, complete WAL horizon, installation readiness, or real-data deployment. A crash can leave decrypted bytes in the exact owner-private scratch; reconcile and remove that scoped orphan under owner procedure. This is not physical-media sanitization.

`Test-VerifyManagedCopy.py --registered` is an isolated `_test` database fixture for exact pre-registered synthetic IDs. It passes its private override values to the same fixed verifier without weakening physical checks, and is not an operator command or an independent authority source.

`review-promotion --report <signed-full-report> --fence-report <signed-fence-report> --approval <first> --approval <second>` is a separate, non-mutating owner review. It verifies canonical detached Ed25519 signatures, a product-audited authority registry/witness revision, bounded expiry, a signed old-writer isolation and credential/session-revocation report bound to the exact qualification digest, and two distinct registered active human owners whose signed approvals bind both report digests, epoch and grant revision. The owner configuration must pre-register each actor/key pair and an independent fence-verification key. A synthetic-only report, missing fencing step, duplicate approver or stale grant is refused. Even a valid evidence set returns `promotionAuthorized:false` and `productCutoverRequired:true`; the product cutover command must recheck live grants and fencing before changing epoch or opening case work. Local signatures or booleans cannot themselves prove a remote endpoint or old writer is isolated.

## Product restored-pair report boundary

Capture success and post-FINISH uncertainty include the original opaque `leaseId` for
`ClaimCore.Database reconcile-backup-capture <lease-id>`. SIGINT during FINISH or OBSERVE reports
`CAPTURE_UNCONFIRMED` and retains the exact files. A hard kill may deliver no diagnostic: preserve
the UUID-named cycle directory immediately under the configured archive root, which is the lease
locator, and its separately held checkpoint files. A missing or changed receipt stays unknown;
starting another capture does not reconcile the first. See the [interrupted owner procedures](../../docs/database.md#interrupted-owner-procedures).
After SEALED and OBSERVED, an output or cleanup failure keeps `CAPTURED_UNVERIFIED` in the safe
stderr diagnostic with the same receipt and lease IDs and a nonzero exit. Reconcile those IDs;
failed stdout is retired so interpreter shutdown cannot retry delivery or append a traceback.

The CHECKPOINT signer acknowledges first signing and exact replay only after the ledger file and
its parent directory are synced. Previously recorded exact signatures remain available after the
new-signing time window; readback does not renew `capturedAt` or the native capture lease. Preserve
the ledger across restarts. Replay signatures are reverified against the original candidate and
configured public key; a damaged record refuses and is not overwritten. Signed deployment
aggregate outputs are also create-only and directory-synced; preserve a failed partial pair and
use fresh output paths only after repeating the required evidence checks.

Exact PEM-file hashes bind the root-signed topology's pinned bytes. Key separation additionally
compares parsed raw Ed25519 keys, so different PEM wrapping cannot make a shared key independent.
This applies to COPY_ATTESTOR/CHECKPOINT, the two promotion approvals, the six observer roles and
their separate aggregate signer, including native product verification. Independent keys alone
still do not establish independent human, host, storage or administrator custody.
Backup configuration must use the installation's exact nonzero 32-byte commitment key and
canonical non-nil key IDs; unsupported material is refused before capture rather than producing
evidence that the native custody reader cannot consume.

`Verify-Restored.sh` invokes only the fixed published `ClaimCore.Database verify-restore-report <report> <signature> <evidence-index> <nonce>` command. The command refuses without an independently reviewed, immutable code-owned publication root; an environment-selected verifier or a callback result cannot install a root. A report and its index are sorted compact ASCII JSON with one LF and a detached Ed25519 signature. Distinct registered RESTORE_REPORT and CHECKPOINT keys/holders must sign their respective evidence. The report binds an exact quiescent backup-capture witness sequence/hash, a later complete auditor-only witness/DataAudit cutoff, primary and witness system IDs/timelines, registered WAL prefix horizons, actual encrypted BASE/WAL object hashes and lengths, owner roster, signed inventory, checkpoint and quiescent audit barrier. The consumer reopens private files through nofollow handles and compares registered copies, catalog, full audit, retained checkpoints and same-timeline WAL prefix coverage. It never converts unknown work into a definite success.

A pre-handoff report explicitly says `recoveryTailUnsealed:true` and `realDataReady:false`. It proves audited facts and a registered WAL prefix, **not** complete recoverability to its later audit tip: the unregistered open tail is a named liability. The quiescent audit barrier does not claim old sessions terminated, endpoint isolation or credential revocation. A separately signed W1 fenced-recovery-tail supplement must later bind the exact report digest and close the open tail through the stopped writer's final endpoint; neither artifact alone authorizes cutover. The current backup capture still emits `unfenced-capture` and unregistered/unverified copies, and this checkout has no reviewed production publication root, so no full signed report is currently issuable from that capture and no real-data promotion is available. Do not relabel these absences as a passing qualification.

`Capture-FencedRecoveryTail.py --config <owner-private-file>` is an isolated synthetic *post-W1* physical-evidence helper for exact-labelled restored PostgreSQL containers. It requires the earlier signed registered WAL horizons, verifies both live system IDs/timelines, forces a real WAL switch on each cluster, copies no more than 1,000 contiguous completed same-timeline segments per cluster, checks each segment with `pg_waldump`, and age-encrypts it. A create-only `0600` metadata file records actual final LSNs and encrypted object IDs, paths, hashes and lengths; stdout is only `fenced-tail-capture=synthetic-only`. The registered CHECKPOINT signer and product `verify-fenced-tail` path must independently bind and recheck this metadata, the exact W1 ticket and the final encrypted bytes. The helper does not register a copy, sign a fence, prove host isolation, or authorize case work. `Test-FencedRecoveryTail.py` covers bounded range, changed-timeline, private-file and no-progress refusals; only an isolated restored-pair Integration test can establish its physical positive.

The capture/inspection protocol is deliberately fail-closed and reports only safe categories. It checks an explicit signed-cycle maximum age and retention interval, but does not yet orchestrate off-host transport, configure PostgreSQL archiving, establish the writer barrier, apply WAL beyond the base-backup endpoint, enforce mutation admission from backup health, verify independent inventory custody, or promote an installation. The service must not treat this standalone tool as an admission gate until those integrations and independent-host qualification exist. Missing archive access, a stale copy, a pending intent, and an unverifiable deletion remain unknown/pending—not recoverable, absent, or erased by inference. `pg_verifybackup` is useful integrity evidence, but PostgreSQL explicitly requires [test restores and checks of recovered data](https://www.postgresql.org/docs/18/app-pgverifybackup.html).

## Independent-host deployment gate

`deployment_probe.py` is an owner-installed, read-only on-host challenge responder. Its private configuration binds exactly one role—primary, witness, archive, checkpoint, or key—to a distinct human custodian actor, an Ed25519 probe-signing key, the physical host and storage being measured, and a role-specific live availability check. Primary/witness probes run a private libpq service read; archive/checkpoint probes hash a selected retained object; the key probe decrypts a fresh age challenge and returns only its SHA-256. Reports contain nonce, short issue/expiry times, owner-pinnable machine/storage commitments, container status and safe availability categories, not paths, database rows or key material. This is an attestation by its signer, not protection against that signer's host administrator.

`deployment_verify.py --config <owner-private-file>` requires five owner-pinned roles and distinct host/storage/custodian/key commitments. It generates a new challenge; reaches each responder through strict SSH with one exact Ed25519 host-key algorithm and SHA-256 pin in a private `known_hosts` file, no ambient SSH config or proxy, batch-only authentication, and a separately pinned probe-signing public key; checks the exact signed nonce, short expiry, installation/lineage/epoch, primary and witness PostgreSQL system IDs/timelines and witness tip, retained object digests, and key identity. It rejects local-test, containerized, same-host, missing or divergent evidence. A copied software age identity proves possession, not independent custody. The pre-W1 `verify-restore-report` command audits the then-current pair only. After W1/P2, while activation is still pending, the deploy gate instead requires the fixed packaged `ClaimCore.Database verify-fenced-tail` command: it re-audits the current pair, verifies the *historical* signed pre-W1 report and every intervening approval/W1 ticket, rehashes the signed encrypted tail, and returns an exact nonce-bound result. Five independently signed host probes must then match the W1 sequence/hash and tail digest; a pre-W1 report cutoff is not a current-tip claim. A code-owned publication root pins the Database binary and RESTORE_REPORT/CHECKPOINT signer identities; owner configuration cannot select a verifier executable or trust root. This checkout has no independently reviewed production publication root or independently hosted/custodied complete fence, so the deploy gate fails closed with `realDataReady:false`. Synthetic injected-root tests exercise protocol mechanics only; neither a hash-pinned stub nor report booleans grant production readiness.

`backup_health.py` parses a short-lived, exact canonical `claimcore-backup-health-1` CHECKPOINT-signed evidence document with both verified BASE copies, both inspected WAL horizons, checkpoint and complete test-restore ages, current generation, activation/W1 history, policy bounds and artifact cutoff. It deliberately has **no issuer**: `managed.py`'s unfenced `UNVERIFIED` copies and config booleans cannot mint a mutation-admission lease. A future owner Database issuer must read witnessed verified rows and independent custody under authority lock; runtime must verify the signed tip as an ancestor of the current witness and check live DB-clock/WAL age. Health is not copy-deletion or ERASURE_FINAL proof. `Test-BackupHealth.py` covers signed synthetic parsing and stale/changed evidence, not a production issuance.

The independent-host verifier also has a root-signed `claimcore-deployment-topology-1` contract: five distinct primary/witness/archive/checkpoint/key probe keys and machine/storage/admin/host-key identities, plus a separately pinned old-writer fence observer. `deployment_aggregate.py` records the exact canonical signed bytes and detached signatures of all six observations in a short-lived, separately signed aggregate bound to the publication manifest, report, fence, W1 supplement, final encrypted WAL object set and challenge. This is necessary input for a product-verified `VerifiedIndependentHostProof`, not a self-issued readiness flag; its `realDataReady` field remains false. Five new-host probes alone cannot establish old endpoint isolation, session termination or credential revocation. The current source has strict observer/aggregate verification and synthetic signature/forgery tests, but no honest old-writer observer issuer or separately hosted qualification on this Mac; product activation must refuse full readiness until those live proofs exist.

`publication_root_record.py` defines a proposed nonce-bound readback for an installation-time immutable publication root: raw Ed25519 public key and SHA, exact signed registration candidate/proof-of-possession, two distinct witnessed owner/steward approvals, independent custodian identity and witnessed registration ticket. The parser does not issue or authorize a root. The fixed owner Database read command must select and verify the sole active witnessed root under authority lock; mutable owner config cannot provide one. An additional reviewed package public-key pin can corroborate it. No such installation root has been provisioned for this checkout, so `deployment_publication_root.py` stays source-pin-unprovisioned and the deploy gate remains closed.

`location_inspection.py` signs a fresh inspection of the exact owner-private copy-location registry under a distinct registered inspector key. The registry binds known copy IDs, installation and witness cutoff, ciphertext digests/lengths, custodian and private location labels; a product export without a managed location is an explicit `UNKNOWN` liability. The owner command recomputes the separate managed-copy HMAC commitments and merges the signed registry with all primary copy rows in keyset pages of 50. A complete known-ID seal may permit live SQL purge while retained or unknown copies keep erasure pending; an `ABSENT` filesystem result alone never proves deletion. The signed input is limited to 8 MiB and 10,000 entries; exceeding that reviewed owner-operation capacity refuses the operation without truncation. It does not discover undisclosed human-held copies, certify physical-media sanitization, or establish separate-host administration.

The operator must first obtain and review each host's machine/storage commitments and pin distinct SSH and probe verification keys under separate administration. Five SSH destinations do not prove separate ownership if one administrator controls every host/key; physical custody and independent administration need a deployment review. No AWS account or permanent paid cloud service is required. The local two-container qualification proves protocol mechanics only; it cannot exercise real separate-host survival or certify production readiness. `python3 eng/backup/Test-DeploymentAdmission.py` exercises only negative cases, including same Mac, missing role, forged signature, stale challenge, owner-pin mismatch, weak SSH pin and absent product recheck.

Run `bash eng/backup/Test-ManagedBackup.sh` for the bounded synthetic drill; it proves encryption and signature checks, `pg_verifybackup`, two actual PostgreSQL restores with recovered-row checks, and altered-manifest/ciphertext, changed-WAL-name and stale-tip refusals. This drill does not use ClaimCore's full schema or DataAudit and therefore is not a full production restore qualification.
